BEHAVIORS

1. Of the commands a daemon records after the one it failed, calling `get_state()` on that same connected client adds none when the failed command was one the daemon never answered, and adds `State` when it was one the daemon answered `result="Error"`.
   kills: treating every failed command alike — keeping the connection after both kinds of failure, or dropping it after both. Keeping it after a stall lets the daemon's late reply be read as the answer to the next command; dropping it after a refusal turns an ordinary refused setting into a dropped connection.
   bite: one-sided by construction — the refusal arm is the anchor and HEAD already matches it, so only the stall arm is red. Measured with `.venv/bin/python scripts/probes/probe_stall_desync.py` against the suite's fake daemon, reading the log from the point the failed command was recorded: after a stalled `SetShaping` HEAD adds `State` where this line requires nothing added; after a refused `SetShaping` HEAD adds `State`, which this line also requires.
   existing: none. `grep -rln "_stall" --include="*.py" .` returns `tests/engine/test_control_stall.py` and `tests/support/fake_control.py` only; the test module was read in full and no case asserts what the daemon received after a fault.

2. In one `apply_live` batch carrying two fields whose first setter the daemon receives and never answers, the second field comes back reported not applied.
   kills: sending the rest of the batch over the same connection after the stall, which reports a value applied that the daemon may never have received and that no readback could have verified honestly.
   bite: HEAD reports it applied. Measured with the same probe: `apply_live` over `{"shaper": "1", "junk_filter": "2"}` on a daemon stalling `SetShaping` returns `shaper: ok=False code=daemon_unavailable` and `junk_filter: ok=True`.
   existing: none. `grep -rn "apply_live" --include="*.py" .` returns four test modules; `tests/apply/test_apply.py::test_one_failure_does_not_abort_the_rest` is the same batch shape with a refused first setter rather than a stalled one, and asserts the opposite outcome.

WIRE AND PROTOCOL FACTS

- One TCP connection to port 4321, each request a complete XML document, responses newline-flushed XML documents read until one parses (docs/protocol.md §1, "Transport and framing").
- The daemon echoes the command element it received, with a `result` attribute of "OK" or "Error", and on error the element text carries the reason (docs/protocol.md §4, lines 125-134).
- "The connection is never dropped on an error — even unknown command elements get an echoed error response" (docs/protocol.md:134). A command the daemon accepts is therefore answered eventually, so a reply given up on is a reply still to come.
- The stall is a field observation, not a hypothetical: hqplayerd 6.0.4 accepted `SetMode` and never answered it while the mode switch took the audio engine down (2026-07-29, quoted in the header of tests/engine/test_control_stall.py).
- `result="OK"` is not proof of application; a live setting is verified by a `State` readback (docs/protocol.md §6 caveat).
