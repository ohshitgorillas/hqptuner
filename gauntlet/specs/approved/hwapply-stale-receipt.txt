The observable surface is the rendered card, not either function: the status line is the element carrying the `hw-status` class, its outcome is a class token beside it (`""`, `busy`, `ok`, `warn`, `err`), and both buttons carry `data-testid="hw-apply"` and `data-testid="hw-revert"`. Each of the six settings carries its own `data-k`: `cuda_offload`, `cuda_dev`, `cuda_cdev`, `multicore_dsp`, `ecore_allocation`, `blocks_per_cycle`.

wire and protocol facts

- The card's apply is `POST /api/engine`, which goes out as a backup-edit-restore on the HTTP config lane and self-restarts the daemon (docs/architecture.md §1 lane 2). It is not a live setter: the four engine attributes have no `/config` field.
- After a restore the daemon serves the pre-restart archive for a read or two before catching up, so the apply's verify rides through a stale window rather than trusting the first read (hqptuner/lanes/settle.py:172-198, paced through the injectable `mgr.sleep`; `tests/apply/test_http_apply.py:98` is an existing case over that window).
- A confirmed apply is the one that answers with `verified.applied`; a submission the verify never confirmed is reported as unconfirmed rather than as success.

applicable fixtures

- `tests/e2e/conftest.py::stack` (session-scoped) — the app under a real HTTP server with the daemon fakes behind it; `stack.http_state` is the fake's mutable state, and a case that edits it puts it back.
- `tests/e2e/conftest.py::page` — a Playwright page against that stack.
- `tests/support/fake_config_xml.py:59-63` — serves `<engine cuda="1" multicore="1" nblocks="16" cuda_dev="-1">`, so the card loads non-default values and every control is live.

The knob that makes "during the round trip" a state rather than a race; put it back afterwards like any other `http_state` edit.
