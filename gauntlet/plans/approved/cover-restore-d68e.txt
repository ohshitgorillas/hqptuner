## The ordering constraint

This is the part that decides the shape of the work, and getting it backwards is how the task fails.

`pre-commit` fires on every `git commit`, including the ones the pair driver makes inside the worktrees: `scripts/pair/trees.py:308` runs `git commit -q -m <message>` with no `--no-verify`. So the floor gate runs at `pair.sh open`, at `pair.sh red` and at `pair.sh merge`, in whichever tree is committing.

`pair.sh open` cuts both worktrees from dev's committed tip, which is `7f865b0e` and does not carry the excision. A pair's trees therefore hold the wall-clock tests still, the floor passes in them trivially, and nothing about the excision is measurable there. That is not a problem to solve; it is the property that makes the sequence work:

1. **The restore lands first, on dev, while the old tests are still present.** Every pair opens from a tip where the floor is already green, so every `open`, `red` and `merge` commit passes the gate on its way in.
2. **The excision stays uncommitted on disk the whole time.** Nothing re-applies it and nothing stashes it. I never write under `tests/` in any tree — `.claude/hooks/tests-lane.py` denies it — so the only hand that could re-apply it is the owner's, and the owner has already applied it.
3. **The excision commits last**, once every replacement is in the tree. At that moment the suite runs against the deletions plus the replacements, which is the state the floor gate has to pass, and it is the first moment that state exists anywhere.

**The hard constraint that falls out of step 2: every file this plan lands must be a file the excision does not touch.** `pair.sh merge` ends in a fast-forward of dev (`scripts/pair/converge.py:138`), and git refuses a fast-forward that would overwrite a locally modified file. The 23 files the excision holds are therefore closed to this plan. Consequences, all of them binding on the spec blocks:

- Every replacement test goes in a **new** test module. No replacement lands in `tests/engine/test_metering_idle.py`, `tests/presets/test_rescan_replay.py`, `tests/apply/test_live_snapshot.py`, `tests/apply/test_manager_apply.py`, `tests/live/test_live_chain.py` or any other file in the excision's list.
- **`tests/conftest.py` is not edited.** The helpers the excision removed from it — `eventually`, `settled`, `_instant`, `running_reader` — are not restored there or anywhere. A replacement that needs a driving seam gets a new module under `tests/support/`, named by its spec block.
- **`tests/support/fake_metering.py`, `tests/support/fixtures_daemons.py` and `tests/support/junk_spectra.py` are not edited**, for the same reason. `MeteringStream` is used as it stands, through its `send(payload, count)` queue path at `:63-67`, never through `repeat=`.

That last point is also what keeps the plan clear of the hazard: the `repeat=` branch is the unbounded one, and nothing this plan lands constructs a `MeteringStream` with it.

**A terminating bound does not discharge this hazard.** `~/dev/CLAUDE.md` 4.6: "A lifetime bound is not a load bound ... A hazard that is load is not discharged by bounding lifetime." A finite iteration count is a lifetime bound. The loop's cost is rate times duration, and a count only shortens the second factor; while it runs, the writer still saturates the loopback at whatever rate the peer will drain. It is also unusable at the size this caller needs: `tests/e2e/support/stack.py:212-247` holds the stream open for the entire life of the app subprocess across a whole browser suite, so any count large enough to serve the run is large enough to saturate for the whole run. The bound has to be on rate, and on this surface a rate bound is a wait.

**Where that wait may legally live.** `docs/testing.md:26` carves `tests/e2e/` out of rule 7, and `scripts/gates/check_test_clocks.py:35` holds `CARVE_OUT = "tests/e2e/"` with `excluded()` at `:38-40` matching it as a substring of the posix path. So the wait is legal under `tests/e2e/` and nowhere else. Two shapes reach that, and stage 1 should choose between them rather than assume:

- **Move the pump.** `MeteringStream`'s `repeat=` branch at `tests/support/fake_metering.py:71-74` plus `spawn_threaded` at `:111` and `spawn_threaded_stream` at `:126` relocate to a new module under `tests/e2e/support/`, carrying the restored `await asyncio.sleep(interval)`. Roughly 40 lines move.
- **Delete the branch and pace from the caller.** `MeteringStream` keeps only its queue path, which parks on `await self._queue.get()` at `tests/support/fake_metering.py:75` and costs nothing while idle — a rate bound by construction, with no clock anywhere in the shared fake. The repeating producer becomes a paced feeder under `tests/e2e/support/`, pushing frames through the existing `send(payload, count)` at `:63-66`. The `repeat=` parameter at `:47-48`, the branch at `:71-74`, and both threaded spawners then have no caller and are deleted, which vulture requires rather than permits. `spawn_threaded_stream`'s own docstring at `:131-132` already states the defect being deleted: "The pump is unbounded: it writes the repeated frame as fast as the peer drains it, which spins a core for as long as a client is attached."

**I recommend the second.** It removes the hazard by deleting the branch that is the hazard, rather than by moving it somewhere the gate cannot see it; it leaves the shared fake with one code path, which is the one every test in this plan's restore already uses; and it shrinks `tests/support/fake_metering.py` instead of duplicating it. Its cost is that the feeder needs the spawner's event loop to schedule onto, which `spawn_threaded` does not currently hand back — so the new e2e module owns the thread and loop as well, and `tests/e2e/support/stack.py:219` changes from `fake_metering.spawn_threaded_stream(_repeat_frame())` to the new module's equivalent. That is one call site, the only one.

Touched files either way: `tests/support/fake_metering.py`, `tests/e2e/support/stack.py`, and one new module under `tests/e2e/support/`. All under `tests/`, and all closed until the excision commits, which is why this is the last step and not the first.

`scripts/strike-diff.py` does not enter this, because no motion block is drafted. The earlier stance stands unchanged where it does apply: a mechanical check that refuses is reported, never worked around.
