What is wrong. The change is implemented and the pair is open; four of the five approved behavior lines are green against it. Line 3 is red in both of its cases for a reason that is not the code: it states the rows a slot's dropdown offers as their data-v values, reading the [Default] row as "", and no row ever carries data-v="". The row is rendered, first in document order, with the attribute present and unvalued, so the reading answers undefined where the line says "". The card offers the right profiles; the observation the line takes is wrong. This plan adds the reading the restated line needs and changes nothing about what the change does or what the user sees.

What is wanted. The Setting Switcher compares two values of one setting with an A/B switch. It covers filters and the shaper today. The owner wants matrix profiles on it too, with the user's profile notes visible in the pickers, and only while the matrix engine is engaged.

What the user sees change. With the matrix engine engaged, the Setting radio group shows a fourth option, "Matrix profile". Picking it shows two dropdowns. Each one lists "[Default]", then every saved profile the engine has loaded, minus whatever the other side has picked. Hovering a row shows the note the user wrote for that profile. A profile the engine has not loaded is not listed. A slot already holding one shows its stored name, and its side takes no click. Pressing A or B switches the running matrix profile. The lit side is whichever slot names the profile the engine reports running. When the matrix engine is bypassed, the row disappears; if it was the picked target, the slots and switch hide, the same way they hide today when a target is not on the loaded chain (ab.js:136-143). The stored pair is kept and returns when the engine is engaged again. Under Direct SDM pass-through, matrix_enabled can read engaged while the daemon runs no matrix (SignalPath.js:216-221). The row stays in that case, because the brief gates on the matrix engine's engaged status. A press sends the same switch the LIVE Matrix profile card sends in that state, and that card is not gated on pass-through either (MatrixProfile.js:59-76).

How it works, by file.
- hqptuner/static/store/live/ab.js: rowsFor (:123) appends a matrix_profile row labelled "Matrix profile" when truthy(runningValue("matrix_enabled")) (runningValue at hqptuner/static/store/resolve.js:241; truthy is what SignalPath.js:23 imports as `on`). Redefinitions this change makes, stated outright: abTarget and AbRow.field (ab.js:58, :94) go from 'the live form field' to 'a switcher target: a live form field or matrix_profile'. AbSlot.id (ab.js:54-56) goes from 'the enum ID that gets written' to 'the value the switch applies: an enum ID, or a profile name, "" for [Default]'. flipAb's contract (ab.js:191-193) goes from 'one live write on the ordinary path' to 'one live write on the ordinary path, or one MatrixSetProfile switch on the matrix profile lane'. The switch is readback-verified by State (hqptuner/lanes/matrixlane.py:35-36) and reported in the card's error line, but it is not a writeLive call. For a profile, AbSlot.name is the profile name at pick time, which is the same string as the id, or "[Default]" for "". So the name-renders rule at ab.js:12-15 still holds, and a renamed or deleted profile renders its stored name. The matrix pair is stored in the same per-field map (:97-98, :159-166) under the key matrix_profile. That key is the same on both chains, so abField (:136-143) finds it directly and TWIN gets no entry. abLit (:182-189) gets a matrix branch comparing each slot's ID, which is the profile name ("" for [Default]), against matrixActiveProfile (hqptuner/static/store/matrix/profiles.js:35-39) with "[Default]" read as "". flipAb (:198-203) gets a matrix branch: it calls api.matrixProfile("switch", name) then refreshConfig, the same two calls the LIVE Matrix profile card makes (MatrixProfile.js:23-34), with its own busy and error signals exported for the card. It never goes through writeLive, because MatrixSetProfile is not a config field (MatrixProfile.js:1-6).
- hqptuner/static/components/live/AB.js: AbBody (:156-190) renders a matrix slot pair and switch when abField is matrix_profile. Slot (:79-112) and Switch (:136-154) take their list and current value from a LiveControl from liveModel, which the matrix profile has none of, so the matrix row gets its own small slot and switch components. The slot uses Combobox. Its options are "[Default]" (value "") first, then each savedProfiles name (profiles.js:65-72) that the engine can reach live. How that empty value reaches a reader is part of what the change delivers, not an implementation detail an observation may assume around: the option row's wire value is rendered as data-v=${o.value} (hqptuner/static/components/controls/comborow.js:81), and SSR emits an empty-string attribute bare (docs/testing.md:138), so the [Default] row carries data-v with no quoted pair and a reader keyed on the attribute's value answers undefined for it, not "". A reading of what a slot offers therefore takes a row carrying data-v with no value as "", which is how the Matrix tab's own saved-profile picker is already read (tests/js/components/matrix/matrixtab.test.js:139-146). The other side's value is dropped from those options. Profiles the engine has not loaded are dropped too, not disabled, which keeps the rule at AB.js:64-67. So the plan no longer reuses the 'not loaded by the engine' reason. Tips come from the Matrix tab's builder. A slot whose stored profile is not among its options shows the stored name as valueLabel, the same way AB.js:99 does. The switch is the same Segment inside `.ab-switch seg-box` that AB.js:143-151 renders, so no new segment size rule is added (docs/design-system.md:49). Under each letter it names the profile its side holds, and an empty side gets no line (tests/specs/ab-slot-label-7f2a.txt:15, :20). A side takes no click in four cases: it is empty, which is AB.js:130-131's rule. Its profile is not offered, again AB.js:130-132. Its profile is a saved name that isLiveProfile rejects. The switch is busy, in which case both sides take no click. A side holding [Default] always takes a click, because the empty name never goes through isLiveProfile; on the opposite side [Default] leaves the menu like any other value the other side holds, since matrixSlotOptions drops the other side's id whatever that id is (AB.js:172-178). That click rule is the Matrix tab Load button's, `!name || isLiveProfile(name)` at ProfileCard.js:86, and it avoids the fallback path at profiles.js:32, which filters "" out. The narrowest state follows from those two together: with the matrix engaged and no profile the engine has loaded, each menu holds [Default] alone, so once one side picks it the other side's menu is empty, that side can hold nothing, and it takes no click. Say a slot names a profile that has a staged delete (profiles.js:69-70). savedProfiles no longer lists that profile, so it is not offered. The slot shows its stored name, and the side takes no click, whether or not the daemon still has the profile. The error line shows the switch's error, so the daemon's refusal with nothing loaded ("Live playback is needed to load a matrix profile.", hqptuner/api/routes/matrix.py:83-88) reaches the user.
