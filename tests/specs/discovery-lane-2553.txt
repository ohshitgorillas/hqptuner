wire and protocol facts:

- The request is one UDP datagram to multicast 239.192.0.199 port 4321, body exactly `<?xml version="1.0" encoding="UTF-8"?><discover>hqplayer</discover>` (docs/protocol.md:26, :29).
- Each daemon answers with `<discover result="OK" name="friendly name" version="...">hqplayer</discover>` (docs/protocol.md:35).
- The sender address of the reply datagram is the daemon host (docs/protocol.md:38). The documented reply body carries no address attribute; line 1's second payload adds one to pin which source the record takes.
- Measured against the 6.0.2 install on this host, the reply is `<?xml version="1.0" encoding="utf-8"?><discover name="Opal" result="OK" version="Signalyst HQPlayer Embedded 6">hqplayer</discover>` from 10.0.0.238, so `version` names the product with the major and never the operating system, and the daemon answers even where it shares a host with the caller. Command: .venv/bin/python scripts/probes/probe_discover_version.py
- The operating system is the `platform` attribute of GetInfo over TCP 4321, verified on 6.0.4 (docs/protocol.md:157).
- Port 4321 refuses connections for about ten seconds after a daemon restart, verified (docs/protocol.md:21), so the UDP answer and the TCP exchange can disagree.
- docs/protocol.md:26 also documents an IPv6 group, ff08::c7. This slice sends on IPv4 only.
