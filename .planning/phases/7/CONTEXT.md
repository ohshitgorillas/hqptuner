# Phase 7: Remove the 4321-only mode - Context

Gathered: 2026-11-09

Feeds: /cad-plan 7

## Scope boundary

In: HQPTuner requires both the 4321 control lane and the 8088 config lane; with 8088 logged out, its credentials refused, or its page or the daemon down, every engine write is refused and the app reads as not working; edits still stage while not ready, Apply does not fire and LIVE edits are held and sent once both lanes are ready; 4321 reads stay attempted and bounded, relied on by nothing; every test app builder and manager fixture rebuilt as the two-lane install; the fake 8088 `/config` page served from the captured 6.0.4 page, with the fake 4321 enumerations matched to it; comments and docstrings describing a 4321-only mode rewritten.

Out: a new auto-open rule for the Connection panel (owner chose the dim, D-07); any new refusal or status-pill copy (D-05, D-17); changing the fake `/matrix` and `/speakers` pages; the allowed-choice check on staged values (phase 8 D-01); any probe against the production daemon.

Deferred: None

Plan shape: multiple plans, same phase (/cad-plan splits it; for example the fakes and fixtures first, then the backend gate, then the UI and comments)

This includes the restart window of an apply HQPTuner itself started (owner ruling, 2026-11-09). Rejected: refusing only LIVE and staged apply, and exempting HQPTuner's own restart. ## Decisions

- D-01 (Readiness): one fact decides "both lanes usable": `ConnectionManager.ready`, which is 4321 `connected` and `readings.http_ok` (false with no 8088 client, a `/config` read error or refused credentials). No new flag. Evidence: `hqptuner/core/manager.py:146-153`, `hqptuner/core/loader.py:69-75,114-123,185`, `hqptuner/core/readings.py:54-66`, `hqptuner/api/routes/status.py:35-42`.
- D-05 (Refusal text): refusals reuse shipped sentences only: `NO_HTTP_CLIENT_MESSAGE`, `AUTH_REFUSED_MESSAGE`, the phase 6 no-answer sentence, and `GetFormFailedError` ("Reading HQPlayer's configuration failed: {error}") for a reachable but unread or errored page. No new copy. Evidence: `hqptuner/conf/httpauth.py:37-47,135-177`, `hqptuner/conf/httpconf.py:144-152`, `hqptuner/api/deps.py:43-50,194-203`.
- D-06 (No client): `http_client is None` stays a reachable state; its branches in `build_http_client`, `decline_error`, `require_credentials` and `presetops.migrate_once` stay as refusals, and only their "not fatal" and "unavailable rather than broken" framing changes. Evidence: `hqptuner/core/connection.py:213-223`, `hqptuner/api/factory.py:48-67`, `hqptuner/presets/presetops.py:312-318`.
- D-07 (Not-working UI): the not-working state is the existing dim: the page stays visible and dimmed while not ready; the Connection panel's auto-open rules stay as they are. Owner answer: "dimming". Evidence: `hqptuner/static/components/App.js:43-52`, `hqptuner/static/css/base/tokens.css:382-384`, `hqptuner/static/store/setup.js:25-28,174-195`.
- D-09 (Health field): `HealthReport.connected` stays, reworded as "the control connection stands", feeding only the Connection panel's latch; its "can still apply a live setting" comment goes. Evidence: `hqptuner/api/routes/status.py:39-42,98`, `hqptuner/static/store/setup.js:105-106`, `docs/openapi.json:1460,1545`.
- D-11 (Refusal tests): tests that assert the not-working answer stay, rebuilt on the two-lane install with the lane taken down mid-run (`_take_lane_down` in `tests/support/fake_http.py`), so no builder starts broken; `unserved_login` survives only as a not-working builder. Tests pinning 4321-only behavior (`tests/js/components/pendingbar.test.js:351-363`, LIVE-success cases on `live_api` and `chain_api`) are removed, or rebuilt on both lanes as owner-approved behavior changes, tests-first. Owner amendment: a test whose subject is startup itself may start an app that has not connected yet, with neither lane answering; no test starts with one lane answering and the other not. Evidence: `tests/api/test_api_errors.py:76-170`, `tests/apply/test_engine_apply.py:60-78`, `tests/api/test_api_error_codes.py:58-62`, `tests/support/apps.py:139-166`.

## Acceptance criteria

- [ ] AC1: with the 8088 lane taken down, its credentials refused or its `/config` page unread, `POST /api/config/live`, `POST /api/volume`, `POST /api/livepresets/{name}/apply`, `POST /api/matrix/profile`, `POST /api/autopilot` and `POST /api/config/apply` each answer a refusal, and the fake 4321 receives no command
- [ ] AC2: in that state, `POST /api/config/stage` succeeds and the edit shows in `GET /api/config/pending`; clicking Apply sends no apply request; LIVE edits made then are sent once both lanes report ready, one write per setting with its newest value
- [ ] AC3: in that state, the 4321 read routes (`/api/state`, `/api/status`, `/api/enumerations`, `GET /api/volume`, `/api/log`) still reach the fake 4321 rather than being refused, and when that fake does not answer or stalls each returns within its deadline on the test clock
- [ ] AC4: no builder in `tests/support/` or `tests/conftest.py` starts an app or manager without both fakes answering and the 8088 forms loaded, except `unserved_login`, and no test asserts a feature succeeding with 8088 down
- [ ] AC5: the fake 8088 `/config` page and `tests/support/fixtures/config-form-6.0.4.html`, parsed by `formparse`, give the same select fields with the same options, and the fake 4321 lists the page's filter, oversampling, dither and modulator IDs
- [ ] AC6: none of the comment and docstring lines listed in D-15 describes a 4321-only mode as supported
- [ ] AC7: `scripts/gate.sh make check` exits 0 on the phase's last `dev` commit

## Flagged assumptions

- Where held LIVE edits live (browser store or backend) and whether they survive a page reload - planner's call; if wrong: a reload while not ready drops edits the user expects to be sent.
- A 4321-up, 8088-silent install never auto-opens the Connection panel under D-07 (`credentials_ok: null`, `everConnected` latched on 4321) - Likely; if wrong: none for D-07, but the user sees only the dim and the red pill with no pointer to the panel.
- Switching the fake 4321 enumerations to the 6.0.4 page's IDs (D-12) leaves the tests that pin today's short chains (`tests/apply/test_manager_apply.py:37-40`, enum 40 at PCM index 1) needing rebuilt values - Likely; if wrong: rebuilt suites pass in phase 7 and fail in phase 8's choice check.
- The fast poll keeps gating on `reachable` under D-03 and tolerates failed reads without an error line per tick - Likely; if wrong: every fast tick with 8088 down draws a visible error.
