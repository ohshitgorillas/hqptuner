# Phase 3: Windows upgrade install - Plan 2: The upgraded app shows its tray icon and no error dialog

## Goal

Installing a new version over an existing one leaves an app that starts cleanly: after the upgrade over v1.20.1 it shows its tray icon and no "Unhandled exception in script" dialog, and `smoke-windows` checks exactly that rather than a proxy for it.

## Must be true when done

- In `smoke-windows` steps 8 and 9, the upgraded app fails the smoke unless the Windows shell holds a notification-area icon registered by one of that app's own windows (ROADMAP criterion 1, tray half).
- In `smoke-windows` steps 8 and 9, the upgraded app fails the smoke if it shows any visible top-level window, and the failure names each such window's title, so an "Unhandled exception in script" dialog turns the run red (ROADMAP criterion 1, dialog half).
- In every `smoke-windows` installer run, a control removes the bundled tray image from the upgraded install and starts that app, and never reads `/api/health` from it. It fails the smoke unless that app has a visible window titled "Unhandled exception in script", the tray query run on that window's own handle answers that no icon is registered, and no tray icon is registered for the app. It then fails the smoke unless the upgraded-app judgment that steps 8 and 9 apply after health rejects the app and names that window. So every run shows the tray query saying "no icon" for a window the app owns, and the judgment going red on the reported symptom (UAT item 7).
- A `smoke-windows` run of the Task 1 commit, where the judgment is still only the existing proxy (PID alive across 5 s), failed at the control because the judgment accepted the broken app after the control had seen its dialog. The executor's report `.planning/phases/3/reports/plan-2.md` records that run before Task 2 starts.
- `check`, `e2e`, `smoke`, `lifecycle-deb`, `lifecycle-rpm`, `smoke-macos` and `smoke-windows` all report success on this plan's last `dev` commit, the arm64 installer row finishes inside the unchanged 15-minute `timeout-minutes`, and steps 1 to 7 and the `windows-bundle-x64` row are unchanged.

## Context

- Gap: UAT item 7 (`.planning/phases/3/UAT.md`, phase 3). `check_upgraded` in `packaging/windows/smoke.sh` accepts the upgraded app on `/api/health` plus "PID alive across 5 s". The build is windowed on Windows (`hqptuner.spec` `EXE` `console=sys.platform == "linux"`), so an unhandled exception leaves the process alive behind a dialog (CONTEXT flagged assumption 3). The step 8 proxy passed on the pre-fix installer in run 42205190797 (SUMMARY open items), so it has never been seen to go red on this symptom. Recalled UAT items 1 and 2 (phases/3/UAT.md, phase 3) are the steps 8 and 9 this plan strengthens; their existing checks all stay.
- Failure path, read in `hqptuner/desktop.py`: `serve` starts the server thread, then calls `parts.browse` and `parts.tray`, i.e. `pystray_icon`, on the main thread with no wait between. That function opens `bundled("data", "tray.png")` with Pillow before `build_tray` creates any pystray object. The spec ships that file as `("hqptuner/data/tray.png", "data")`, which lands at `{app}\_internal\data\tray.png`. So removing that one file reproduces the reported `FileNotFoundError` in the tray load exactly, the case D-01 calls a broken install, and on that install no pystray window ever exists.
- Health on the broken app is a race, and nothing may depend on it. Whether uvicorn answers `/api/health` on its daemon thread before the main thread's tray load raises is not ordered by the code. The plan review read PyInstaller 6.22.3's `runw.exe`: it resolves `PyErr_Fetch`, `PyObject_Str` and `Py_Finalize` by name but none of `PyEval_SaveThread`, `PyEval_ReleaseThread` or `PyGILState_*`, so the main thread keeps the GIL while the dialog is open and the server thread stops running from then on. That reading was not repeated on this host, which has no PyInstaller bootloader in its caches. The kernel still accepts connections on the bound socket, so a health probe of a frozen server times out rather than being refused.
- pystray 0.19.5 `_win32.py` (the version in this host's uv cache; `pyproject.toml` leaves it unpinned) has three relevant facts. Its `_register_class` names the window class `'%s%dSystemTrayIcon' % (self.name, id(self))`. `_run` creates two hidden top-level `WS_POPUP` windows of that class, deliberately not message-only. `_message` calls `Shell_NotifyIcon` with `hWnd=self._hwnd`. It also passes `hID=id(self)`, but `_util/win32.py` `NOTIFYICONDATAW` names that field `uID`, and ctypes keeps an unknown keyword as a plain attribute. I checked that locally (`S(hID=...)` leaves `uID` at 0). So the icon is registered as (tray window, uID 0).
- PyInstaller 6.22.3 (the current release; `release.yml` installs it unpinned) shows the error through `DialogBoxIndirectParamW` in its windowed bootloader `runw.exe`. That binary carries the UTF-16 strings `Unhandled exception in script` and `Failed to execute script '%ls' due to unhandled exception: %ls`.
- Locked and out: no change under `hqptuner/`, no fallback around the tray image (D-01); `hqptuner.iss`, `release.yml` and `timeout-minutes` (owner ruling in SUMMARY deviations: `smoke-windows` stays at 15) are untouched; steps 1, 2a and 7 stay intact (D-08); the bundle row keeps its path (D-07); no human Windows 11 check. Patterns to follow in `smoke.sh`: `signed` passes a path to PowerShell through the environment because PowerShell reads everything after `-Command` as script text; `lan_address` and `describe_lookup` show inline PowerShell; step 4's lookup self-check ("or an empty answer in step 1 proved nothing") is the precedent for a check proving its own detector bites.
- Local tools: `shellcheck`, `bash -n`, `scripts/gate.sh make check`. No Windows runner here; `smoke-windows` runs only on an owner push of `dev`. Baseline: `shellcheck -S warning packaging/windows/smoke.sh` exits 0.

## Tasks

### Task 1: a broken-tray control in step 8, which the existing upgraded-app judgment fails, run red on an owner push

- **Files:** packaging/windows/smoke.sh (`check_upgraded`, `upgrade_quit`, `cleanup`, a new PowerShell-backed helper beside `lan_address`, the header comment)
- **Action:** Add the control that tests the upgraded-app judgment against the reported symptom. This is the tests-first half of the plan (`docs/testing.md` rule 8): the control lands here in its final form, and Task 2 does not edit it. Run it once per installer run, in step 8 (`upgrade_quit`), after `check_upgraded` has passed and stopped the healthy upgraded app, and before `uninstall_upgraded`. One path is enough, because steps 8 and 9 share `check_upgraded`. Breaking and starting the app: first require that `$UPGRADE_APP/_internal/data/tray.png` exists; if it does not, die naming the path, so a bundle layout change cannot make the control vacuous. Then delete that one file and nothing else under `{app}`. The uninstall that follows still needs `unins000.exe` and `unins000.dat`. Start `$UPGRADE_APP/HQPTuner.exe` from the smoke, the way `start_previous` starts v1.20.1: `BROWSER` set to `/usr/bin/true` in Windows form, `LOCALAPPDATA` set to the path's `UPGRADE_DATA`, and `HQPTUNER_LISTEN_HOST` set to `$LISTEN_HOST`, as step 3 sets it for a Start Menu launch. Find its Windows PID with a bounded `running_under` lookup, as `check_upgraded` does, and die unless there is exactly one. Make that PID one that `cleanup` stops, so a death anywhere in the control leaves no process behind (`~/dev/CLAUDE.md` 4.1). The detector: add a read-only helper that takes a Windows PID and reports every top-level window that belongs to it (`EnumWindows`, `GetWindowThreadProcessId`): its handle, its class name, whether it is visible (`IsWindowVisible`), its title, and the result `Shell_NotifyIconGetRect` returns for a `NOTIFYICONIDENTIFIER` carrying that window's handle and uID 0, the uID pystray 0.19.5 actually registers (see Context). Query every window of the PID, not only pystray's, so the query's answer for a window with no icon is on the record. Use inline PowerShell as `lan_address` and `signed` do, passing the PID through the environment the way `signed` passes `SIGNED_FILE`; Win32 calls go through `Add-Type`. From that report, the tray icon counts as present when a window whose class name ends in `SystemTrayIcon` answered S_OK, and absent otherwise. Match the class name on pystray's suffix only, never on "HQPTuner", because the prefix comes from `build_tray`'s icon name inside `hqptuner/` (`docs/testing.md` rule 9). The helper is read-only: no window is closed, shown or sent input, and no icon is added, modified or removed. The control's own evidence that the symptom is present: give the dialog a bounded wait in the script's style to appear, then require three things of the broken app's PID. It has a visible window titled exactly "Unhandled exception in script", the caption PyInstaller's windowed bootloader uses (see Context). The helper reports a query result for that window, and the result is not S_OK. The tray icon counts as absent. Die naming whichever of the three did not hold. The control never reads `/api/health` from the broken app, because its server may never answer (see Context), and the control must reach the same answer whichever way that race falls. The verdict under test: factor the judgment `check_upgraded` applies after its health loop out into one unit that both `check_upgraded` and the control call, so the two cannot drift. In this task that judgment is exactly today's check, the PID alive across the same 5 s window. It returns a verdict with the findings behind it instead of ending the script; the shape is the executor's choice. `check_upgraded` turns a rejection into `upgrade_die` with the message it prints today, so its behavior on steps 8 and 9 is unchanged by this task. The lookup, the health loop, the address check and the stop stay in `check_upgraded`, outside the shared judgment. The control calls the judgment on the broken app once its three symptom checks hold. If the judgment accepts, die with a message saying the upgraded-app check accepted an install whose tray image is missing. If it rejects without naming the "Unhandled exception in script" window among its findings, die printing the findings it gave. The control passes only on a rejection that names that window, and prints the findings. Either way, stop the broken app by PID with `stop_and_wait` before `uninstall_upgraded` runs, because a process held open by a dialog has to be stopped with force. `stop_windows_pid` already uses `taskkill /F`. Every other step is unchanged. Update the header comment so it states that a broken tray load must be caught, keeping comments to what holds now (triviajudge). After this commit, execution pauses for the owner's push of `dev`. The executor never pushes.

### Task 2: the upgraded-app judgment requires the app's tray icon and no visible window

- **Action:** Add the helper's two findings to the shared judgment Task 1 factored out, after its 5 s alive window. The judgment is the direct check of ROADMAP criterion 1; the alive window stays as the check that the process did not exit. A healthy app has no visible top-level window, because `BROWSER` runs `true.exe` as a separate process and pystray's windows are hidden. Do not edit the control: with this change its call to the judgment rejects the broken app and names the dialog, which is what turns it green. If the green run shows a healthy upgraded app failing the tray half, stop and go back to the owner with the run's lines. That failure would mean either that `Shell_NotifyIconGetRect` does not answer across processes or for an icon in the overflow area, or that the runner has no taskbar. Swapping the query for another documented read of the same registration counts as a deviation, which the executor logs. This is internal CI work with no user-visible change, so `CHANGELOG.md` gets no entry; the repo rule lets internal-only work skip it.
