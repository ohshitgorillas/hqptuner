# Phase 3: Windows upgrade install - Plan 1: Upgrade over v1.20.1, quit or running

## Goal

Installing a new version over an existing one leaves an app that starts cleanly, whether the old version was quit first or left running in the tray.

## Must be true when done

- In `smoke-windows`, after v1.20.1 is installed and its app stopped by PID, the new installer run over it into the same directory leaves an upgraded app that is still running after its tray is built and answers `/api/health` at the runner's non-loopback address (AC1).
- In `smoke-windows`, with the v1.20.1 app left running during the new install, no v1.20.1 process remains when the installer returns, and the upgraded app is still running after its tray is built and answers `/api/health` at the non-loopback address (AC2).
- After each upgrade, the uninstaller leaves no install directory behind (AC4).
- A `smoke-windows` run carrying the upgrade steps against the pre-fix `hqptuner.iss` failed at an upgrade step, and that run is recorded before the installer fix lands (AC3).
- `CHANGELOG.md` `[Unreleased]` `### Fixed` carries the owner-approved entry for the upgrade fix, verbatim (AC5).
- `check`, `e2e`, `smoke`, `lifecycle-deb`, `lifecycle-rpm`, `smoke-macos` and `smoke-windows` all report success on the phase's last `dev` commit, with the fresh-install steps 1, 2a and 7 and the `windows-bundle-x64` row unchanged (AC6).

D-04: `AppId`, `DefaultDirName`, `PrivilegesRequired` and both `[Files]` entries stay as they are. D-05: `InitializeSetup`, the `[Registry]` HKCU write and `LaunchWanted`/`/LAUNCH` stay as they are.

### Task 6: The installer closes a running HQPTuner.exe and clears `{app}\_internal` before it copies files

- **Action:** Both halves of D-01 and the changelog entry land in ONE commit. Each half is a user-visible change, and the repo's changelog rule wants the entry in the same commit as the change, so neither half is committed without the other or without the entry. Close half: make Setup close a running `HQPTuner.exe` from the install directory before any file is copied, in silent and interactive installs alike (D-01, D-02). My choice of mechanism: set `CloseApplications=force` in `[Setup]`. The other option was a `[Code]` stop. The default `yes` already asks the Restart Manager to close apps holding files Setup replaces. `force` adds a forced shutdown, which a tray app with no visible window is expected to need. The Restart Manager matches by open file, not by path spelling. So the 8.3-versus-long spelling problem `running_under` had to solve does not arise, and no new user-facing text is added: the interactive Preparing page uses Inno Setup's own built-in messages. Leave `RestartApplications` at its default. The app does not call `RegisterApplicationRestart`, so nothing is restarted, and `/LAUNCH` stays the only silent launch (D-05). Do not touch `AppId`, `DefaultDirName`, `PrivilegesRequired`, the `[Files]` entries (D-04), `InitializeSetup`, `[Registry]`, `[Run]` or `LaunchWanted` (D-05). Do not add `AppMutex`: it needs a mutex in `hqptuner/desktop.py`, which is out of scope. The CI green run may show a v1.20.1 process still alive at Task 3's check. That stop waits until they are gone, returns an empty string so it adds no user-facing text, and is logged as a deviation. Never stop by image name alone, because that would kill another install's app. Clear half: make Setup remove the whole `{app}\_internal` directory of an existing install before `[Files]` copies the new bundle (D-01). Use an `[InstallDelete]` entry of type `filesandordirs` naming `{app}\_internal`. Inno Setup processes it after the Preparing step, where the close half closes the app, and before any file copy. Never name `{app}` itself or anything outside `_internal`, because `unins000.exe` and `unins000.dat` live in `{app}` and are what Task 4's uninstall relies on. A fresh install has no such directory, so the entry does nothing there. D-04's directives and entries and D-05's code stay as they are.
