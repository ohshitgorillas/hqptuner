# Phase 4: API exposure and authentication - Plan 1: The login and the gate behind it

## Goal

Findings F-001, F-002, F-003, F-008, F-009, F-024, F-025, F-027 and F-028 are each fixed or carry an owner ruling. This plan delivers the server half of the login (D-01, D-04, D-05, the cookie half of D-06): a browser logs in with the HQPlayer management pair checked against hqplayerd, and every `/api` route but `/api/health` and the login itself refuses a caller without that login.

## Must be true when done

- Without a login cookie, every `/api` route except `/api/health` and the login route answers 401 with the shared `{"detail", "code"}` shape, a loopback caller included; `/api/health` still answers 200 to anyone (AC1, first half).
- With the cookie from a successful login, every existing REST test passes unchanged apart from the added login, which is the suite's proof that each route answers as it does today (AC1, second half).
- A login with a wrong pair answers 401 and sets no cookie; a correct pair sets one that is `HttpOnly` and `SameSite=Strict`; "log in every time" sets a cookie with no expiry and "save password" sets one with an expiry, which still authenticates after HQPTuner restarts over the same state (AC2, D-01, D-06 cookie half). The server refuses a "save password" login older than that expiry and a "log in every time" login older than 24 hours.
- A login never fills a blank password from the pair HQPTuner holds, and its "save password" choice decides only that browser's cookie: no login changes the stored connection record's `remember` choice. A browser that changes the pair through the Connection panel stays logged in while every browser logged in under the old pair is logged out.
- `.planning/security/REPORT.md` is tracked and byte-identical to `/tmp/secreview/REPORT.md` (D-14, first half).
- `scripts/gate.sh make check` prints `exit=0` and `make test-e2e` passes on this plan's last commit.

## Context

- Locked: D-01 (per-browser login with the HQPlayer pair, no loopback exemption, no separate password), D-03 (no Host allowlist), D-04 (one app-level gate in `create_app`, `/api/health` open), D-05 (cookie carrier, because `EventSource` and the download links cannot send a header), D-06 (cookie not sent cross-site), D-13 (every test caller logs in), D-15 (user-facing text only as owner-approved). Recalled: D-01 and D-03 (phases/4/CONTEXT.md, phase 4); the risk surfaces auth, secrets, untrusted_input and api_contract (phases/1/SUMMARY.md, phase 1) are why the login tests below go past the happy path.
- Read in this tree: `hqptuner/api/factory.py` `create_app` adds no middleware and takes `clock` as its injected seam, whose `now` is the wall-clock read (`hqptuner/core/clock.py` `Clock.now`; `tests/support/virtual_clock.py` `VirtualClock` fixes it through its `now` argument); `hqptuner/api/routes/connection.py` `write_connection` saves the record, calls `layer_onto_config`, `build_http_client`, `manager.retarget`, `manager.refresh_http_forms` and `manager.audit.connection_set`, and `_remembered` reads the stored `remember` choice (no record reads as no); `hqptuner/conf/httpconf.py` `HttpConfigClient` speaks Digest through `httpx.DigestAuth` and `hqptuner/conf/httpauth.py` `raise_for_status` turns 401/403 into `AuthRefused`; `hqptuner/api/errors.py` `STATUS` owns every code's status and `docs/architecture.md` §8.1 lists them.
- `tests/support/fake_http.py` accepts any `Authorization` header unless its state sets `_refuse_auth` (403 on a digest), `_challenge_auth` (401 challenge first) or `_down` (503). 31 test files build the app (`create_app(` appears in each file listed in this plan's frontmatter under `tests/`). `tests/conftest.py` `_no_daemon_but_the_fakes` holds the default 8088 port closed, so a test app with no fake cannot reach any daemon to log in against; Task 5 gives such apps a fake (owner ruling c in Notes). `fake_http.spawn` sets `_take_lane_down` on the state, which stops the listener so a new connection is refused.

### Task 3: Login tokens that only HQPTuner can mint, bound to the pair in force

- **Files:** hqptuner/core/login.py, hqptuner/config.py, tests/api/login/test_login_token.py
- **Action:** Add, in the `core` layer, the login token: a value HQPTuner mints when a login succeeds and later checks on every gated request. It is an HMAC over a per-install secret and a fingerprint of the username and password in force, plus the login's kind ("save password" or "log in every time"), its issue time and a random nonce, compared in constant time (`hmac.compare_digest`). Kind and issue time ride inside the signed value, so neither can be changed without failing the check. A token is refused once it is older than its kind allows: a "save password" token past one fixed lifetime, the executor's choice, defined once in this module and read by Task 4 as its cookie's `Max-Age`, so the cookie and the server agree; a "log in every time" token past 24 hours, which bounds a browser session the user never closes. Time comes from the app's existing `clock` seam (`Clock.now`): minting takes the issue instant and checking takes the current instant from the caller, and this module reads no clock of its own, so a test sets the instant (a plain instant at the store lane, `VirtualClock(now=...)` at the REST lane) and never waits on a wall clock (`docs/testing.md`: slow tests are defects). Binding it to the pair means a change of username or password ends every login made under the old pair, and a restart that leaves HQPTuner without a password (a "log in every time" record stores `""`, `hqptuner/core/connection.py` `ConnectionStore.write`) ends every login, which is the same moment today's panel asks for the password again. The secret: random bytes from `secrets`, held in memory from startup, and written to a file beside the connection record (the directory of `Config.connection_file`) only when a login asks to stay logged in across restarts; once that file exists it is read at every start and its value is the secret. When it is first written, write the secret already in memory, so tokens issued before it was persisted keep verifying; create it exclusively so two first writers cannot leave two secrets, with owner-only permissions where the OS has them. A session-only login writes nothing to disk, so a login that does not ask to stay logged in changes no file (Plan 2's lifecycle check and the test suite both rely on that). Put the file's name where both `core` and the `presets` export can import it without inverting a layer edge: `hqptuner/config.py` already holds `CONNECTION_STORE`'s name; do not add the file to `Config.STORES`, which would ship it in every state export, and add no `Path` field to `Config`, which `scripts/gates/testing/check_e2e_isolation.py` would then require the e2e stack to redirect. A secret file that exists but cannot be read raises the existing store errors (`StoreCorruptError`, `StoreUnwritableError`) at first use, never at app construction: HQPTuner must still start and answer `/api/health` on a broken state directory. Reading the secret happens once per app; minting and checking never touch the disk.
- **Verify:** Testing scope, at the store lane (rule 15), the lowest that sees these outcomes: a token minted for a pair verifies for that pair; it fails for another username, for another password, after any byte of it is changed (the kind and the issue time included), and under another install's secret; a "save password" token checked one second inside its lifetime verifies and one second past it fails; a "log in every time" token checked one second inside 24 hours verifies and one second past it fails, and at one age past the shorter of the two limits and inside the longer, a token of the longer kind verifies while one of the shorter kind fails, so the check applies each kind's own limit; every age is set by the instants passed in, with no wait; a secret persisted by a save-password login is the one a fresh instance over the same directory reads, so the token survives a restart; a token minted before the secret was persisted still verifies after; a session-only login leaves the directory with no new file; on POSIX the persisted file is readable by its owner only. That is the whole contract; the gate's REST tests in Task 7 cover the wiring. Bite: new module, discharged statically by naming the null stub (a check that accepts every token), which every "fails for" case fails against. `scripts/gate.sh .venv/bin/pytest tests/api/login/test_login_token.py -q` and `scripts/gate.sh make check` both print `exit=0`.

### Task 4: The login route

- **Files:** hqptuner/api/login.py, hqptuner/api/routes/connection.py, hqptuner/api/factory.py, hqptuner/api/errors.py, docs/architecture.md, docs/openapi.json, tests/api/login/test_login_route.py, .filepawl.toml
- **Action:** Add a login route in its own module under `hqptuner/api/routes/`, so phase 5's work on `connection.py` (F-004, F-021) and this route do not collide in one file (CONTEXT flagged assumption 3). It takes a username, a password, the "save password" choice the Connection panel's two radios already carry as `remember`, and an optional host. It checks the typed pair with Task 2's check against the host the login names, or the host in force when it names none, at the `hqp_http_port` in force, and answers: accepted sets the login cookie and answers 200; refused answers 401 with a new login-refused code and sets no cookie; not answered answers a 503-class refusal with its own code and sets no cookie. The cookie carries Task 3's token, `HttpOnly`, `SameSite=Strict` (D-06: never sent on a cross-site request, a top-level navigation included), `Path=/`, and no `Secure` flag, because every package serves plain HTTP and a `Secure` cookie would never be sent back. `remember` on a login decides only that browser's cookie (D-01: a login affects that browser only). "Log in every time" (`remember` false) mints Task 3's "log in every time" token and sets a session cookie with no `Max-Age` and no `Expires`, so it ends when the browser session does; "save password" (`remember` true) mints the "save password" token and sets `Max-Age` to Task 3's lifetime, the one value, stated in `docs/architecture.md`. The token's issue time is the app's `clock` reading at the login. Three rules bind the route. First, a blank or missing password is checked as blank: the route never fills a field from the pair HQPTuner holds, because that is the stored credential working for a caller who does not know it (F-001). Second, the host: there is no host rule (owner ruling in Notes). A login naming any host is checked against that host, on a fresh install or a configured one, and is never refused for the host it names. Third, a login never writes the connection record because of `remember`: the panel's form defaults `remember` to true (`hqptuner/static/store/setup.js` `form`) and a logged-out page cannot read `GET /api/connection`, so a login that wrote its `remember` would let one browser store a plaintext password against an install's "Ask every time" choice, or blank a stored one. An accepted login whose pair, or whose named host, differs from the pair and host in force applies them exactly as `write_connection` applies a save today (record write, `layer_onto_config`, `build_http_client`, `manager.retarget`, the forms refresh, `manager.audit.connection_set`), so a login naming another host retargets as a Connection-panel save does; the record it writes carries the stored `remember` choice that `_remembered` reads (no record reads as no), never the login's. Move that sequence into one function both routes call rather than copying it, with the `remember` it writes as its caller's to pass: caller-side delta, the sequence moves out of `write_connection` and is called from 2 sites, `write_connection` in `hqptuner/api/routes/connection.py` (passing the save's `remember` as today) and the login route (passing the stored choice). An accepted login whose pair and host match those in force writes no record and touches no lane, whatever its `remember`. `create_app` gains no argument for the pair check: the route calls Task 2's function, and every test logs in over the wire against `tests/support/fake_http.py` (owner ruling c in Notes). Register the route in `create_app`, add every new code to `STATUS` and to the `docs/architecture.md` §8.1 table, and state the login in §2.4 Credentials as a normative rule (one login per browser, checked against hqplayerd at the host it names, the cookie and its two lifetimes, `remember` deciding the cookie only). The refusal sentences (`detail`) are user-facing copy and ship only in the owner-approved wording listed in this plan's Notes (D-15): the login-refused `detail` is the approved panel verdict, the not-answered `detail` is the approved sentence `hqptuner/static/lib/api.js` `unexplained` already answers a 503 with, both verbatim; no new sentence is written for this route. Regenerate `docs/openapi.json` with `scripts/gates/check_openapi.py --write`. Run `filepawl accept` whenever filepawl prints it.
- **Verify:** Testing scope, REST lane, over the real wire against `tests/support/fake_http.py`, with no stand-in for the pair check: a wrong pair (`_refuse_auth`) answers 401 with the login-refused code and no `Set-Cookie`; a correct pair answers 200 with a cookie that is `HttpOnly` and `SameSite=Strict`; with "log in every time" that cookie carries neither `Max-Age` nor `Expires`, with "save password" it carries `Max-Age` equal to Task 3's lifetime; a daemon that does not answer (closed port) answers the not-answered code and no cookie; a blank password with a chosen password in force is checked as blank (the executor chooses how the test observes the pair that reached the daemon); a login naming a host other than the one in force, on an install with a saved record, is checked against that host (a second `fake_http` instance on another loopback address accepts while the one in force refuses with `_refuse_auth`, and the login answers 200), and once accepted `GET /api/connection` reports that host; an accepted login with a new pair leaves `GET /api/connection` reporting the new username; with the pair and host in force, a login whose `remember` differs from the stored record's leaves the record file byte-identical in both directions (a stored "save password" record under a "log in every time" login, and a stored "ask every time" record, password blank, under a "save password" login); an accepted login with a new pair over a stored "ask every time" record writes `remember` false and a blank password; an accepted login that changes nothing leaves the record file as it was. Stop there; the gate and every route behind it are Task 7's. Bite: the route is new, so the static discharge names the null stub (the route answering 200 and setting nothing), which the refused, no-cookie, expiry and other-host cases fail against, and a second stub (the route writing the login's `remember` into the record), which both `remember` cases fail against. `scripts/gate.sh .venv/bin/pytest tests/api/login/test_login_route.py -q`, `scripts/gate.sh .venv/bin/python scripts/gates/check_openapi.py` and `scripts/gate.sh make check` all print `exit=0`.
