# Phase 4: PCM filters in SDM output mode - Plan 1: SDM filter apply without a reset

## Goal

A user in SDM output mode can apply PCM filters without the engine resetting.

## Must be true when done

- AC1, as CONTEXT words it: a commit on `v2` names the path that reset the engine, and a test that reproduces the reset on the fake daemons fails at the commit before the fix and lands before it. If Tasks 1 and 2 stay green and Task 3's red run shows only the refused stage, no test reproduces a reset and AC1 is unmet as worded. The executor then stops after Task 3, before Task 4, and takes AC1 back to the owner for a ruling. It does not reword AC1 itself.
- With the engine in SDM mode, a filter picked on the Resampling drawer's SDM tab "PCM sources" rows is accepted by the stage call, with no 422, and the Apply that follows sends one `SetFilter` and nothing else: no `POST /restore`, no config form POST, no `SetMode`.
- With the engine in SDM mode, a 1x or Nx filter written through `POST /api/config/live` (the page pick, the bottom switcher, Filter presets and Easy Mode all write this way) sends one `SetFilter` and no `POST /restore` or `SetMode`.
- In PCM output mode, applying a PCM filter still sends `SetFilter` as it does today. The existing tests in `tests/live/test_live_apply_split.py` pass with no edits.
- `scripts/gate.sh make check` prints `exit=0` at the phase's last commit.

## Context

- "PCM filters in SDM output mode" means the SDM chain's filters for PCM sources: catalog keys `sdm_filter_1x` and `sdm_filter_nx`. Their register fields are `oversampling1x` and `oversampling`, written by `SetFilter` args `value1x` and `value` (D-01). The idle "PCM out" tab (`pcm_filter_1x`, `pcm_filter_nx` while SDM runs) is deferred. So are the tests and spec rows that pin its restore (D-02).
- The cause is found from the code and from red tests on the fake 4321 and 8088 daemons. It is never found by a live probe of the production daemon or by reading the hqplayerd journal. It is recorded in a commit before the fix lands (D-03). The three suspects are in D-04.
- "No reset" means the only engine write is `SetFilter` on the loaded chain (D-05). PCM-mode filter apply stays unchanged (D-06). Tests come first, through the fake daemons and the JS store, with no wall-clock wait (D-07).
- What planning found in the code (the executor confirms it, and does not take it on trust): the server serves every `SetFilter` field with `lane: "live"` (`hqptuner/fields/register.py` `_read_lane`). The `dsp.js` catalog entries carry no `liveKey`, by design: commit 2cbbd0c0 restored the schemas "without client lane metadata", and `docs/spec/api.md` says "Clients keep no lane table". So `stagedSlot` in `hqptuner/static/store/schema.js` returns live bucket `""`. `POST /api/config/stage` refuses `""` with `fields_unknown`, because `query.stageable()` does not contain it. The server's routing (`routing.split_live`, `is_staged_route`) expects these fields as form edits in the `http` buffer, and routes them live on the loaded chain. The live route (`routing.resolve_live`, then `lane.apply_now`) sends only `SetFilter` for `oversampling1x` and `oversampling` on the SDM chain.
- Out of scope: any change to `hqptuner/lanes/`, `hqptuner/api/`, `hqptuner/core/`, the idle "PCM out" tab, `CHANGELOG.md` (the owner's alone), and any user-facing text.
