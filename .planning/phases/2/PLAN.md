# Phase 2: Windows network access - Plan 1: Installer-started launch on the network

## Goal

A fresh Windows install answers on the PC's network address from the first launch on, including the launch the installer starts itself.

## Must be true when done

- On a Windows machine with no HQPTuner, the app the installer starts at the end of setup answers `/api/health` at the machine's non-loopback address.
- After that app is stopped and the installed exe is started again the way a Start Menu launch starts it, the new process answers `/api/health` at the same address.
- A silent install without the launch switch leaves no `HQPTuner.exe` process running; a silent install with it starts the app exactly as the finish page does.
- `smoke-windows` exercises the installer-started launch and failed at that step's address check against the pre-fix installer.
- `README.md` no longer says the Windows app is reachable from that PC only, tells users to allow HQPTuner on Private networks, and `CHANGELOG.md` `[Unreleased]` carries a Fixed entry, both in owner-approved wording.
- `check`, `e2e`, `smoke`, `lifecycle-deb`, `lifecycle-rpm`, `smoke-macos` and `smoke-windows` pass on the phase's last `dev` commit.

## Context

- D-01: the fix is `[Code]` in `hqptuner.iss` setting `HQPTUNER_LISTEN_HOST=0.0.0.0` in Setup's own process environment before the `[Run]` entries; the `[Registry]` HKCU\Environment write stays; `hqptuner/config.py` keeps its `127.0.0.1` default. D-02: an opt-in `/LAUNCH` switch runs the postinstall launch during a silent install; without it a silent install starts nothing.
- D-05/D-06: today's smoke masks the bug (step 1's `/VERYSILENT` skips the `[Run]` entry, step 3 exports the registry value itself). The new step finds the installer-started app by lookup, records and kills its PID, passes `LOCALAPPDATA` and `BROWSER` on the installer invocation, and checks `/api/health` at `lan_address`; step 3 stays for criterion 2; the `windows-bundle-x64` row keeps skipping the address check.
- D-07: the bite proof is a red smoke-windows run on an owner push to `dev` with the new step against the current `hqptuner.iss`, before Task 5 lands. `release.yml` runs only on path-filtered pushes and has no `workflow_dispatch`.
- Out: the code default listen host, the single-instance probe in `hqptuner/desktop.py` (`launch`), any Windows Defender Firewall rule from the installer, and phase 3's upgrade-install `FileNotFoundError`.
- No ISCC and no Windows runner exist on this host; the `.iss` compiles in `package-windows` and runs in `smoke-windows`, both on an owner push. `shellcheck` is local; its current baseline on `smoke.sh` is two SC2016 infos only.

### Task 2: smoke-windows checks that a silent install without the switch starts nothing

- **Files:** packaging/windows/smoke.sh (step 1, the helpers above it, `cleanup`)
- **Action:** Right after a `/VERYSILENT` install that carries no `/LAUNCH`, the smoke looks up running `HQPTuner.exe` processes whose image lies under that install's directory and dies with a `step 1:`-style message naming the PID if any is found (AC4). The `[Run]` entries execute before Setup exits and the outer setup.exe waits for its inner process, so the lookup runs immediately on the installer's return with no sleep or polling window; a wall-clock wait here would be a slow-test defect (`CLAUDE.md`, `docs/testing.md`). Do the lookup from PowerShell (`Get-Process` path or `Get-CimInstance Win32_Process` executable path, the executor's choice) in a helper beside `user_env` and `lan_address`, passing the directory through the environment as `signed` does, because PowerShell reads everything after `-Command` as script text. The helper returns Windows PIDs, which Git Bash's `kill -0` and `kill` do not address; anything that later checks or stops such a PID uses a Windows-PID-aware call. Bundle targets skip this check. This is a characterization of behavior that already holds (`skipifsilent`), so it has no pre-change state to fail against; that exemption from `docs/testing.md` rule 8 is stated in the hand-back.
- **Verify:** Testing scope: one negative check, on the two installer rows; it stops there, no permutation of other switches. Locally `bash -n packaging/windows/smoke.sh` exits 0 and `shellcheck -S warning packaging/windows/smoke.sh` exits 0 (the two existing SC2016 infos are below that level), and `scripts/gate.sh make check` prints `exit=0`. In CI (required job `smoke-windows`, owner push): both installer rows pass step 1 including the new check, and the `windows-bundle-x64` row is unchanged.

### Task 3: smoke-windows exercises the installer-started launch at the network address

- **Files:** packaging/windows/smoke.sh (a new step between step 2 and step 3, `cleanup`, the header comment)
- **Action:** For installer targets only, the smoke runs a silent install with `/LAUNCH` and checks the app the installer itself started (AC1, AC3, D-06). On the installer invocation set `LOCALAPPDATA` to a fresh directory under `$WORK` and `BROWSER` to `/usr/bin/true` in Windows form, as step 3 does, so the inherited child neither touches the runner's real stores nor opens a browser. The installer invocation must not carry `HQPTUNER_LISTEN_HOST`: step 3 `export`s it into the shell, so the new step runs before that export, and it removes the variable from the installer's environment explicitly so a runner that has it set cannot mask the bug. After the installer returns, find the installer-started process by the Task 2 lookup, die if there is not exactly one, and record its Windows PID; extend `cleanup` so a failing run also stops that PID. Wait for `GET /api/health` on `BASE_URL` to answer 200 (bounded tries as step 4 does, dying if the PID is gone) so a start failure reads differently from the bug; then fetch `/api/health` at `lan_address` and die with a message naming this step and the address check when it is not 200. That line is what AC3's red run must show. Then stop the process by its PID and confirm by PID that it is gone within a bounded wait, so step 3's "something already answers" guard and its registry-environment launch run unchanged as criterion 2 (AC2). Never install over a present install: phase 3's upgrade bug is out of scope and would confound the result. So the AC4 install of Task 2 and this `/LAUNCH` install are two installs with an uninstall between them, and the run still ends with step 7's checks after the last uninstall. Which install comes first is the executor's choice. Keep step 4's existing address check, and keep the bundle row skipping every address check. Update the header comment to name the new step's purpose. This task must not touch `hqptuner.iss`.
- **Verify:** Testing scope: AC1 and AC3 are uncovered today (D-05); this one step closes both, on the x64 and Arm64 installer rows; AC2 stays with the existing step 3, and no further check is added.
